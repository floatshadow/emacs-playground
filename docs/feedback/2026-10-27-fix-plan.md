# Fix plan for the newcomer review (2026-10-27)

The bug tracker is [2026-10-27-newcomer-review.md](2026-10-27-newcomer-review.md): bugs B1..B18, ranked recommendations R1..R10, the stuck moments and the "smaller things" at its end (here S1..S5). This plan gives each item an owning area, its root cause in code, the fix, and the exact check the verifier runs. Items found during triage that the review did not number are X1..X4 (X5 to X8 were found while fixing, X9 and X10 during integration, X11 and X12 after the verification of the merged main); the check latency the review measured is L1.

Areas (AGENTS.md §2): **web** (`web/**`), **curriculum** (`curriculum/**`), **emacs** (`emacs.d/**`, `images/session/**`), **backend** (`cmd/**`, `internal/**`, including `internal/protocol` and the generated `web/src/protocol.gen.ts`). "Primary" owns the item and its verification; "with" names an area that must change something for the item to pass.

How the bugs were reproduced: the running local stack (gateway, session and remote-box images built from `a0c0f3d`), headless Chrome 124 driven with playwright-core, the `/s/local/events` stream recorded in the page, `emacsclient --eval` inside the session container for Emacs internals, and `playctl curriculum play` for replays. Every item below was reproduced unless the root-cause column says otherwise.

**The verification script** is `web/e2e/review.mjs` (committed with this plan). It encodes every check in the last column against the behaviour *after* the fixes, so on the current code most checks fail; §7 records that baseline. Run it against the local stack with Chrome on CDP :9222:

```sh
cd web && node e2e/review.mjs                   # all checks, about 6 minutes
PG_REVIEW_ONLY=B1,B4 node e2e/review.mjs        # a subset
```

It writes `artifacts/review/<id>.png` and `artifacts/review/results.json`, prints `PASS`/`FAIL` per check with evidence, and resets all progress when it finishes. Checks that need a fix in another area to pass say so in their output.

## 3. Contracts

These are the API additions recorded in [docs/api.md](../api.md) (§2.4, §2.6, §3.4, §4, §4.1). The backend owns every change under `internal/protocol` and lands it first, in one small commit with `make protocol` (the regenerated `web/src/protocol.gen.ts`); the web works against those types. Names below are exact.

### (a) Progress reset ("Start over")

- `POST /api/v1/progress/reset` with body `{lessonId}` clears that lesson's records (as today). With no body, `{}` or `{"lessonId": ""}` it clears every record of the user. Response `204`. Audit action `progress.reset` with `lesson=<id>` or `lesson=*`.
- The gateway then calls the session's internal op `drop-step` with `{lessonId}` or `{}` (best effort, as today). sessiond: with a lesson id it forgets that lesson's saved progress and the active step if it belongs to the lesson; without one it forgets all saved progress and the active step. Whenever an active step is forgotten it emits `step {lessonId, stepId, status:"dropped", index, count}`.
- Start over clears progress only: workspace files, checkpoints and the module set stay (each lesson's setup restores its own files).
- Web: the course map gets a **Start over** button next to Continue, and the Session page a **Start over** button in a Progress section. Both open a dialog titled **"Start over?"** ("This clears the progress of every lesson: ticks, hints and resets. Your files and Emacs stay as they are.") with **Cancel** and **Start over**. On confirm the web posts with no body, refetches progress, and clears its own per-session memory: `completed`, `reopened`, `lessonsComplete`, `checks`, hint levels, `habitsSeen` (also in localStorage), dismissed cards; `activeStep` clears on the `dropped` event. A finished lesson's completion box gets **Start this lesson over** (posts `{lessonId}`, then `rpc scenario {lessonId, reset: true}`).
- Web step list (fixes X1): the engine's active step of this lesson is always shown active, whatever progress says. Steps after it never show a tick (they will be evaluated again when reached). Steps before it show this visit's outcome (`complete` → done, `demonstrated`, `skipped`) or else their progress status when it is `done`, `demonstrated` or `skipped`, or else not done. With no active step in the lesson, this visit's outcomes and progress decide.
- Resume (web `resumeStep` and sessiond `Engine.FirstIncomplete` agree): the first step whose status is neither `done` nor `skipped`; a `demonstrated` step is resumed so the learner practises it.
- Scripts: `web/e2e/smoke.mjs` and `web/e2e/review.mjs` post a reset with no body in a `finally` when they finish (the local, git-ignored verification scripts do the same); `playctl curriculum play` resets each lesson it played when its `-session` URL is a gateway session path (`…/s/<id>`), controlled by `-reset-progress` (default true for such URLs, false for sessiond itself).

### (b) Watch it is a demonstration

- New RPC op `demo`, body `{stepId, phase: "start" | "end"}`, result `{restored: bool}`. `409 conflict` unless `stepId` is the active step.
- `start`: when the engine counted any command since the step started or was last reset, sessiond first restores the step's checkpoint (files and windows, exactly as `restore {}`, emitting `step {status:"reset"}`, but without counting a reset) and answers `restored: true`. Then it sets the step's **demo latch**. From then until the step is reset (`restore`, Reset this step, Do it yourself), reloaded (`scenario`) or dropped, a completion of the step is recorded as `demonstrated`, not `done`: progress status `demonstrated`, event `step {lessonId, stepId, status:"demonstrated", index, count}` (once), no advance, no next checkpoint. The step stays active. Stuck rules are not evaluated while a demo plays.
- `end`: the player finished or was stopped. Only the "playing" flag clears; the latch stays.
- `restore {}` (the active step's checkpoint) clears the latch, as does any reload of the step. Completing the step afterwards without a demo is recorded `done` and advances as today.
- Web: Watch it calls `demo start`, plays the demo at **600 ms per chord and 120 ms per typed character** (`~N` pauses as written), and calls `demo end` in a `finally`, also when the learner's keypress stops it. While it plays, the ticker area shows a caption strip (`role="status"`, `aria-label="Demo caption"`): "Watching: <goal>", the keys sent so far left to right with the current one highlighted, typed text growing inside quotes, and a Stop button. The screen header does not change (B7). After a `demonstrated` event, or after any demo start on the active step until the next `reset` event, the step shows a hollow check, "You watched this step. Now do it yourself." and a primary **Do it yourself** button that calls `rpc('restore', {})`. A learner keypress during the demo stops it as today.
- Inline "try it" buttons (`:try[…]`) keep sending keys as learner input; a step they complete is `done` (decision 5).
- playctl keeps its own pacing (170/70 ms, `protocol.DemoChordDelayMs`/`DemoCharDelayMs`) and never sends `demo`, so its replays still record `done` (and are reset afterwards, contract a); `-watch` (R1) is the exception.

### (c) Skip this step

- New RPC op `skip`, body `{stepId}`, result `{next: string | null, demoCompleted: bool}`. `409 conflict` unless `stepId` is the active step. Not idempotent; it takes as long as the demo (at most 60 s).
- sessiond restores the step's checkpoint when commands ran since the step started (as in `demo start`), then plays the step's `demo` itself through the terminal (tmux, playctl pacing 170/70 ms) with completion recording suspended; `demoCompleted` says whether the conditions held afterwards (false is logged as a curriculum defect). Then it records progress `skipped`, emits `step {status:"skipped", index, count, lessonComplete}`, takes the next step's checkpoint and emits `step {status:"loaded"}` for it (`next` is its id; after the last step `next` is null and `lessonComplete` true). A step without a demo is skipped without replay. The same server-side player fast-forwards "Go to this step" (B2).
- Web: in the I'm stuck dialog, after the report is sent the body changes to "Thanks, the report was sent. If you would rather move on, Emacs can do this step for you." with **Skip this step** and **Close**. Skip calls `rpc('skip', {stepId})`, shows an overlay over the screen ("Emacs is doing this step for you…") that keeps the learner's keys from the terminal until the call returns, then a toast "Skipped: <goal>". Skipped steps carry an arrow mark and "skipped" in the step list. The course map shows skipped steps: a done row reads "done", a row whose steps are all `done`, `demonstrated` or `skipped` but not all done reads "finished · N skipped · M watched" with a hollow mark, an in-progress row adds "· N skipped" when there are any.

### (d) Nudge suppression

- Mentioned keys: the key sequences in the current step's `goal`, `detail` and every condition `hint`, and in the lesson's Markdown (backticked spans that parse as keys with `KEY_RE`, `:kbd[…]`, `:try[…]`), normalised with `normalizeKeysLoose`.
- A habit card for key K is suppressed when some mentioned sequence starts with K (`C-s` in 1.4 suppresses "C-s is not save"; `C-x C-s` in 0.1 does not). A mentioned span may hold several commands (`C-a C-k` in 3.5 and 2.7: C-a, then C-k), so "starts with" applies to each command of the sequence: it is cut after every key that is not a prefix key (`mentions.ts` `commandsOf`, `PREFIX_KEYS`; added after the verification of §7). The pattern nudge `many-windows` is suppressed when `C-x 2` or `C-x 3` is mentioned, and fires only when the learner split a window (a split command in the ticker): windows that pop up, such as 2.7's build output, are no accident. A suppressed card does not count as seen.
- `habitsSeen` persists in localStorage under `pg.habitsSeen.<sessionId>` (a JSON array of normalised keys), read when the session id is known and written when a card fires; Start over clears it. Dismissed ids stay per page session.
- Dismissing a card removes only that card; habit cards have no command TTL (B9).
- No API change.

## 4. Decisions

1. Watch it restores the step's checkpoint before playing whenever the learner ran a command since the step started, so a demo always starts from the state it was written for (B2's demo failure). The learner's partial work in that step is lost; the caption says "Starting from the beginning of this step".
2. Progress status order, highest first: `done`, `skipped`, `demonstrated`, `in-progress`, `not-started` (`protocol.ProgressRank`). A report never lowers a step's status; only a reset clears it. A lesson is `done` only when every step is `done`; GET `/progress` also returns per-lesson counts (`counts: {done, demonstrated, skipped, total}`).
3. Start over resets progress and the browser's per-session memory, not files, checkpoints or modules.
4. Skip plays the step's demo server-side from the step's checkpoint, so the next step finds the state it expects.
5. Inline "try it" keys count as learner input: they are a nudge, not a demonstration (task decision; R4's second sentence is not adopted).
6. Habit cards have no command TTL; at most three show; Rescue moves above "Did you mean" (B9).
7. The engine's debounce becomes 40 ms trailing with a 120 ms cap (L1); the 1.5-2.2 s figure is not a server delay.
8. The ticker is per lesson: cleared when a step of another lesson loads. A reload still starts it empty.
9. Focus mode works in the page first and upgrades to fullscreen with the keyboard lock when the browser allows (B14).
10. "Go to this step" and "Do this step again" restore that step's checkpoint after the lesson setup, or fast-forward through the earlier demos when there is none (B2, X2).
11. The rail collapses at 1440 px instead of 1180 px (S5).
12. ws-butler's lighter is hidden rather than explained (B16/R8): it never asks anything of the learner.
13. The GUI's X screen follows the browser pane's size (noVNC `resizeSession`) instead of being scaled (B13).
14. `review.mjs` is the acceptance test for this plan; fix agents run the checks for their items and the verifier runs all of them.
15. Every checkpoint restore keeps `emacs.d/modules.el` (found while fixing B2: "Go to this step" now restores step checkpoints, and a checkpoint taken before a module change put the older set back on disk under a running Emacs with the newer one, so the next lesson load restarted Emacs for nothing).
16. The fast-forward of decision 10 rehearses each earlier step in the engine (conditions evaluated, nothing recorded or emitted) and waits up to 10 s for it before the next demo; the `scenario` RPC returns when the target step is active (at most 3 minutes). The web's resume target goes through the same path, so reopening a lesson mid-way starts the step from its checkpoint.
17. If Emacs cannot close its X connection when leaving GUI mode, Xvnc is left running (reused by the next switch) rather than stopped under Emacs (B12).
