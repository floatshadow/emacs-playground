Learn Emacs by working in it, with every keystroke explained.

A browser tutorial around a real, fully configured Emacs. Real projects in Rust, OCaml, Python, Typst and LaTeX. A key ticker that names what you just did, a panel that always knows how to get you out, and checkpoints when you want to try again.

Two ways to run it

On your machine

One learner. Build or pull the images, open a browser. Your work and your growing init.el live in a folder on the host.

git clone … emacs-playground && cd emacs-playground
docker compose --profile local up      # pulls prebuilt images, or --build
open http://localhost:8080

# the same Emacs in your own terminal, keyboard protocol and all
docker compose exec session tmux attach -t emacs
  • No login, no orchestrator: compose starts one session container.
  • ./workspace is bind-mounted, so projects and the config survive restarts and can be copied to a real machine.
  • Bring-your-own-terminal mode: kitty or WezTerm attach to the tmux session while the browser shows only the lesson and the ticker.

On a server, for a group

Many learners. The same images; the gateway starts one isolated session container per person and reaps idle ones.

cp .env.example .env     # DOMAIN, auth mode, limits
docker compose --profile server up -d
# Caddy terminates TLS; gateway talks to Docker through a socket proxy
  • Per-learner named volume for the workspace; progress in the gateway's SQLite database.
  • Invite codes or OIDC login; CPU, memory, pids and disk limits per session; idle stop after 30 minutes, volume kept for 30 days.
  • Session containers: read-only root, dropped capabilities, no Docker socket, egress only to package registries.

How "live" hints stay tractable the part that looks impossible

Learners can go wrong in endless ways, but Emacs can only be in a small number of states that swallow input. Almost every "what just happened?" is one of them. So hints are layered: three universal layers that need no per-lesson work, and one declarative layer per step.

  1. State exitsThe agent reports real Emacs state after every command: minibuffer open, prefix pending, isearch, extra windows and what they show, recursive edit, narrowing, overwrite, read-only, macro recording, suspended, frame closed, Dired instead of a file. A table maps each state to one exit. This is the "Where am I" panel. It works in every lesson and project because it reads state, not intent.authoring cost: one table row per state; grows with modules (magit-status-mode, eshell, pdf-view-mode)
  2. Habit translation and stuck patternsPure functions over the recent key stream. VS Code habits that mean something else in Emacs get one card each (C-z suspends, C-s searches, C-a is line start). Three C-g in a row, the same unbound key twice, typing into a read-only buffer, twenty seconds inside a prompt: each has a calm, fixed response.authoring cost: a habits table and about ten pattern rules, shared by everything
  3. Goal distance per stepA step declares ordered conditions, each with one hint: "the prompt was used", "main.rs is current", "the text changed", "saved". The hint shown is always the first unmet condition. Authors describe the goal, never the mistakes; the engine finds where the learner stopped.authoring cost: three to five conditions per step, as YAML and elisp or shell predicates
  4. Reset, then telemetryWhen hints fail, Rescue restores Emacs's UI state and Reset restores the step's files and layout from a git checkpoint. Because the environment is fully pre-configured and reproducible, this is always safe. The event log around an "I'm stuck" click shows which new table row to add. Optionally, a model can narrate the last twenty events as a last resort.authoring cost: none per lesson

What a lesson author writes

# curriculum/02-files/03-opening-files/scenario.yaml
id: 02-files/03-opening-files
mode: terminal            # terminal | gui | any
modules: [base, completion] # config modules unlocked so far
setup:
  workspace: fixtures/hello-rust   # copied to /work/hello
  open: [hello/README.md]
  layout: single
steps:
  - id: open
    goal: Open src/main.rs
    demo: "C-x C-f ma TAB RET"
    conditions:
      - text: the Find file prompt was used
        event: { command: find-file }
        hint: C-x then C-f. The prompt is the bottom line.
      - text: main.rs is the current buffer
        elisp: (equal (buffer-file-name) "/work/hello/src/main.rs")
        hint: Type ma, press TAB, then RET.
  - id: save
    goal: Save it
    conditions:
      - text: saved
        all:
          - { event: { command: save-buffer } }
          - { file: { path: hello/src/main.rs, not_contains: "Hello, world" } }
        hint: C-x C-s. The mode line shows ** until you do.
vscode: Ctrl+P, Ctrl+S

The prose is a Markdown file next to it. Key names inside backticks become keycaps; a {try} directive makes one clickable and sends it to Emacs. Checks come in four kinds: an event (a command ran), an elisp predicate evaluated inside Emacs over the client socket, a file matcher, and a shell test. They are re-evaluated on every agent event, debounced.

Entering a step records a checkpoint: a git ref over the workspace plus a buffer and window spec. Reset restores both. The scenario also names which config modules are unlocked, so part 0 starts close to vanilla Emacs and part 9 ends with the full setup, without hiding any of it.

Projects use the same format with longer steps, more than one workspace root, and a remote block that provisions the SSH box.

The chrome borrows Emacs's own violet and a pale lilac paper, so the dark modus-themed screen sits in a margin rather than fighting a second dark UI. Type: Source Serif 4 for prose and interface, a mono face (Iosevka when installed, JetBrains Mono otherwise) for keys and the screen.

One bold element: the keycap ticker under the screen, which names every chord, its command and a plain gloss, and shows a pending prefix as a waiting state. Everything else is quiet: rules instead of cards, no shadows, numbering only where there is a real sequence (steps). Visible focus rings, reduced-motion respected, layout collapses to two then one column.

Decisions to confirm before building

  1. Terminal frame first, GUI frame for media lessons. Crisp text, faithful keys, cheap sessions; the same Emacs daemon serves both frames so switching never loses buffers. Alternative: GUI-only over VNC, simpler but blurrier and heavier.
  2. Vanilla Emacs keys, not evil. The goal is to learn Emacs. An evil track can be added later as a module.
  3. Eglot over lsp-mode, package.el + use-package over elpaca/straight. Built-in first, so what you learn transfers to any Emacs; alternatives are shown in part 9.
  4. Go for the gateway and sessiond, React + Vite for the web app. Static binaries, a strong standard library, and a widely known stack for maintainability.
  5. Emacs 31.1 (released August 2026: built-in which-key, completion preview, user-lisp/, mouse on by default in terminals). Fallback to 30.2 if a needed package lags.
  6. xterm.js 6.1 beta with the kitty keyboard protocol plus kkp.el in Emacs, so C-;, C-RET and friends work in the terminal frame. The 6.0 stable release cannot distinguish them.
  7. English UI first, Chinese later through the same string tables.
